## Existing offline behavior

Source inspection confirms parsed receipts, people/groups, assignments, and active tab persist locally through [page.tsx](src/app/page.tsx) and [session-persistence.ts](src/lib/session-persistence.ts); thumbnails also use localStorage. Editing/calculation is local; new receipt/URL parsing requires connectivity. Optional server receipt storage/webhooks remain separate from local session data.

The [production precache](src/app/serwist/[path]/route.ts) includes page shells, scripts, styles, and fonts: web can reopen offline after successful caching. Bundled assets supply that shell on iOS. Preserve this behavior and verify it on devices; no offline parsing/sync system is needed. Use a small native-backed persistence adapter because WebView storage can be evicted; preserve migrations and load saved data before autosave. Safari data does not automatically transfer into the app. [Storage guidance](https://capacitorjs.com/docs/guides/storage)

- [ ] Run TestFlight; resolve feedback. Prepare opaque icon/launch assets, required screenshots, listing text/category, privacy/support URLs, age rating, export compliance, regional information, accessibility claims, and sample receipt/review steps. Archive/sign/upload, submit app/IAPs, address findings, manually release after approval, and verify live installation. [Submission guide](https://developer.apple.com/app-store/submitting/)
- [ ] **Before launch: clean up the v1 placeholders.** The iOS Settings sheet (`src/components/app-settings.tsx`) and the `/privacy` and `/support` pages (`src/app/privacy/page.tsx`, `src/app/support/page.tsx`) are deliberately minimal and plainly styled; restyle them as part of the broader UX revamp. Before submitting: set `NEXT_PUBLIC_SUPPORT_EMAIL` so the pages show a real address; have the trimmed privacy policy (recipients described by category, no vendor names) checked against the actual data handling and against Apple's third-party AI disclosure rules (guidelines 5.1.1 and 5.1.2), and decide whether the consent dialog must name the AI provider (bump `CONSENT_VERSION` if its promises change); keep `docs/ios/privacy.md` and `docs/ios/review-notes.md` in sync if the AI, screenshot, or storage provider changes.
- [ ] **Storage mirror limits (accepted for v1, verify on a device).** The Preferences backup (`src/mobile/native/storage.ts`) is a simple write-through copy: at launch it only restores keys the WebView lost, and a key the WebView still has wins. Two known edge cases: (1) if a `localStorage` write fails (quota) but the Preferences write succeeds, the next launch keeps the stale local copy and overwrites the newer backup, losing the last edit; (2) if the app is killed before a queued Preferences delete finishes, a deleted split can reappear after New Split. Neither corrupts data. Check on a real device (eviction, kill during New Split) and harden only if it shows up in practice.
- [ ] **Privacy manifest and SDK audit (needs a Mac).** `ios/App/App/PrivacyInfo.xcprivacy` is a draft: remove Product Interaction (the iOS bundle has no analytics SDK), decide and declare the Venmo phone-number entry to match `docs/ios/privacy.md`, and inspect the manifests Xcode embeds for the plugins (including CapacitorTipJar) for required-reason APIs.
- [ ] **Tip completion event.** `TipJarPlugin.swift` emits `tipCompleted` for deferred (Ask to Buy) purchases and the transaction is finished natively, but no JS listens, so the UI never learns it completed. Wire a listener in `src/mobile/native/tip-jar.ts` or drop the event.
- [ ] **Native chrome in e2e.** `e2e/mobile` serves `dist-mobile` in plain Chromium (web platform), so the iOS Settings sheet is not covered end to end, and the suite is not run in CI. Add a native-platform path and decide whether to wire it into CI.
- [ ] **Web behavior change to confirm.** Dismissing the system share sheet no longer copies results to the clipboard on the web (it did on `main`); the platform layer reports `"cancelled"`. Keep or restore.

## Release and maintenance

1. Merge tested changes to main; web deploys and provides early feedback while remaining usable production software. **Shared API changes affect installed apps immediately**, so freezing mobile UI does not freeze its backend.
2. When ready, set version/build numbers and tag the candidate commit (`ios-v1.0.0-rc.1`). From Linux, check out that revision in a dedicated Mac build directory over SSH, install dependencies, build/sync assets, and invoke Xcode's command-line tools; test through TestFlight. Fixes get new candidate tags/builds; do not move tested tags.
3. Submit manually; record commit, build, toolchain, and notes in a draft GitHub Release. Once approved/available, publish it with a final tag (`ios-v1.0.0`) pointing to the tested commit. Releases do not automatically build/submit anything. [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
4. Keep v1 API changes additive; deploy support before mobile features. Check the oldest supported app against staging. Preserve stored sessions/link formats; define eventual deprecation without blocking saved offline splits. Web/backend rollback must remain compatible; faulty installed binaries need corrective releases.
5. Monitor parsing failures/cost, native crashes, retention, and dependencies. Even during quiet months, retain alerts/reminders for membership, credentials, SDK/policy deadlines, and OS compatibility. Those may require maintenance releases without new features.

Verify the Mac's SSH hostname/user, connectivity, Xcode, and signing access before relying on remote builds. As of 2026-11-02 the Linux box's SSH key is rejected by the Mac, so Mac work runs through a T3 Code agent on the Mac or locally. The laptop must be awake/reachable during builds; initial signing/Keychain setup and interactive debugging may need local attention. Routine work stays on Linux. Hosted macOS CI remains an optional later replacement for the laptop. [Command-line builds](https://developer.apple.com/library/archive/technotes/tn2339/_index.html)

**Linux build path (updated 2026-11-02):** xtool is not the build path. On Linux it builds SwiftPM apps for physical devices only, cannot target the iOS Simulator, and does not fit this Xcode project with SwiftPM binary dependencies and StoreKit. Native builds run on the Mac with `xcodebuild` and `devicectl` (`npm run ios:device`). Linux handles web, tests, `npm run mobile:dev`, and browser previews (add `?native` in dev to see the iOS layout).

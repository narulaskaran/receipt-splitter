# iOS app

Receipt Splitter on iPhone is a Capacitor 8.6 app. The native project lives in `ios/` (Swift Package Manager, deployment target 26.0, iPhone only). It ships a bundled copy of the shared React UI and talks to the Next.js site on Vercel for parsing. The website and the API stay on Next.js. There is no separate Swift UI.

This document is the map. Account setup, signing, TestFlight, and device checks are manual and were not run here. Each of those steps is marked UNVERIFIED in the other files in this directory.

## What is bundled

`npm run mobile:build` writes a static client to `dist-mobile`. Capacitor's `webDir` is `dist-mobile` (`capacitor.config.ts`). `npx cap sync ios` copies that folder into the Xcode project. The committed config has no `server.url`, no `cleartext`, and no `allowNavigation`. A release build loads the bundled files. It does not load a dev server.

The iOS bundle does not include the Next.js service worker, the share-target route, or server-only modules. Offline editing of a split that is already on the device is local state. Parsing a new receipt still needs the network. Uncached visits to `/privacy` and `/support` on the website fall through to the existing offline page. Those routes were not added to the precache list (`/`, `/split`, `/offline`).

## Origins

Configuration is `src/lib/app-config.ts`.

| | Web | iOS |
| --- | --- | --- |
| API | Same origin as the page (`apiOrigin` empty) | `VITE_API_ORIGIN`, an HTTPS origin of this backend |
| Share links | `NEXT_PUBLIC_SHARE_ORIGIN`, else the page origin, else `https://receipt-splitter.app` | `VITE_PUBLIC_ORIGIN` |
| Version header | none | `VITE_APP_VERSION`, sent as `X-Client-Version` |

Share links must be ordinary `https://` URLs on the public site. They must not use `capacitor://localhost`. The API allows the Capacitor origin through CORS (`NATIVE_APP_ORIGINS` in [backend-setup.md](backend-setup.md)). CORS is not authentication.

Tip product IDs default to the three consumables in `src/lib/tip-products.ts`. Override them at mobile build time with `VITE_TIP_PRODUCT_IDS` (comma-separated). See [tips.md](tips.md).

## Build flow

```bash
npm run mobile:build
npx cap sync ios
```

On a Mac, open `ios/App/App.xcodeproj`. Linux can run the two commands above and `npm run ios:check`, which reads the committed project and fails if a dev server setting, a wrong deployment target, or a drifted bundle id lands in git. `ios/App/App/capacitor.config.json` is generated by `cap sync` and gitignored. When it exists, `ios:check` requires it to have no `server` key. When `dist-mobile` exists, `ios:check` requires `index.html` and no `http://localhost` references.

`npm run ios:sync` is the mobile-tooling name used in [release.md](release.md) for the Mac build directory (asset build plus `cap sync`). It is provided by the client build scripts.

## Linux and Mac

On Linux:

- `npm run dev` for the website.
- `npm run ios:check` for the committed native project.
- `node scripts/generate-ios-assets.mjs` to rebuild the opaque icon and splash from `assets/app-icon.png`.
- Do not commit a temporary `server.url`. `ios:check` rejects it.

On a Mac (UNVERIFIED: no Xcode, simulator, or device was available here):

- [ ] UNVERIFIED: install a current Xcode, open `ios/App/App.xcodeproj`, and run the App scheme on an iPhone simulator or device.
- [ ] UNVERIFIED: a live-reload `server.url` is a local, uncommitted experiment only.

Confirmed on Linux: the Xcode project sets `IPHONEOS_DEPLOYMENT_TARGET = 26.0`, `TARGETED_DEVICE_FAMILY = 1`, and `SUPPORTS_MAC_DESIGNED_FOR_IPHONE_IPAD` / `SUPPORTS_XROS_DESIGNED_FOR_IPHONE_IPAD` / `SUPPORTS_MACCATALYST` to `NO`. `npx cap sync ios` rewrites `Package.swift` and sets `platforms: [.iOS(.v26)]` to match that deployment target. Do not hand-edit `Package.swift`. CI runs sync and fails if the committed file drifts.

## What was checked here

Checked on Linux, without a Mac:

- `npm run ios:check` against the committed project.
- The privacy and support pages build as static routes.
- The app icon and splash were rewritten by `scripts/generate-ios-assets.mjs`, and sharp reported them opaque.

Not checked:

- Compiling the iOS app, signing, or installing it.
- StoreKit purchases, the camera, or any other plugin on a device.
- App Store Connect, TestFlight, or review.

## xtool

xtool is optional and is not the architecture. On 2026-10-30, xtool 1.24.0 on the Linux build machine resolved Capacitor 8.6 and the app, camera, share, and preferences packages, including a separate SwiftPM wrapper. Native compilation was not verified: Apple's SDK download requires a signed-in developer account and was deferred. xtool does not take the stock Xcode app as input, and its signer creates development profiles. Ignore it for release builds until compilation, device and StoreKit behavior, and distribution signing are actually shown to work. Release builds use Xcode on the Mac, as in [release.md](release.md).
